## 1.1 什么是 Apache Doris？

### 同一份订单数据，两类工作

客户提交订单时，业务系统需要确认客户、校验商品数量和价格，再保存订单及其明细。
这次操作关注一笔交易是否正确完成。例如，订单已经创建成功，关联的商品明细也应当完整保存。
围绕业务操作进行查询、校验和提交的工作，通常称为联机事务处理（OLTP）。

运营同事查看“本周每天的订单金额”时，关心的是一批订单的整体情况。
系统需要读取日期范围内的订单，把同一天的记录放在一起，再计算数量和金额。
这类面向数据集合的统计与探索，通常称为联机分析处理（OLAP）。

两类工作都可能使用 SELECT。判断它们时，可以问自己：这条查询服务于哪一个业务目标？
“查出订单地址，供客户修改”服务于交易操作；“按客户地区比较订单金额”服务于经营分析。

| 对比点 | 交易处理：提交一笔订单 | 分析处理：查看每日订单金额 |
| --- | --- | --- |
| 业务目标 | 完成并记录一次业务操作 | 理解一段时间内的业务表现 |
| 常见访问方式 | 按订单号访问少量记录，并执行写入或修改 | 按日期筛选多笔记录，再关联、分组或聚合 |
| 关注的问题 | 操作是否成功，关联数据是否一致 | 指标口径是否准确，数据是否及时，查询是否稳定 |
| 本课程中的位置 | 源业务系统 | Doris 分析层 |

例如，每日报表最后只展示七行，背后仍可能读取一周内的数百万笔订单。
结果行数反映展示粒度，读取的数据范围则决定了计算需要处理多少业务记录。

### Apache Doris 为这类分析提供什么？

Apache Doris 是开源的实时分析数据库，支持使用 SQL 查询明细、关联多张表和计算汇总指标。
在本课程中，业务系统继续记录交易，Doris 接收这些业务数据，供分析师和看板查询。
[产品定位与使用场景](https://doris.apache.org/docs/4.x/getting-started/what-is-apache-doris/)

对数仓用户来说，这意味着从“找一笔订单”到“按日期、客户或商品分析一批订单”，
可以围绕同一套数据逐步展开。先查清明细，再形成稳定的指标和看板，是本课程的学习路径。

大批量分析需要有效地读取和计算数据。Doris 的列式存储按列组织数据：计算订单金额时，
查询可以读取所需的日期、金额等列，减少对其他业务字段的读取。
它的 MPP（大规模并行处理）架构支持多个节点协同执行查询。
你仍然提交一条 SQL，由数据库规划数据扫描、计算和结果汇集。
这些机制如何受到表设计和写入批次影响，将在 D02、D03 中继续展开。

Doris 提供 MySQL 兼容协议接口，因此可以使用支持该协议的客户端或驱动连接。
本课的 Notebook 通过 Python 工具提交 SQL，后续 BI 工具也通过数据库连接访问数据。
连接方式可以复用熟悉的工具；SQL 功能和事务行为以 Doris 的支持范围为准。

### Doris 位于数据到业务结果的哪一段？

```text
订单、支付等业务系统
        ↓ 历史导入 / 持续接入
    Doris 中的业务数据
        ↓ 校验、清洗、关联与汇总
    可供查询的明细与指标
        ↓ SQL 客户端 / BI 连接
      分析师与业务看板
```

这条链路包含三个需要分别完成的工作：接入数据、整理数据、交付分析结果。
建立数据库连接只完成了访问准备，持续接收源系统变化还需要配置导入或同步任务。

举个例子：一笔订单的状态在业务库中发生变化，要让看板反映新状态，需要接入任务把变化送到
Doris，目标表按既定规则处理新旧记录，最后由查询或刷新后的结果向看板提供数据。
数据新鲜度由整条链路共同决定。本课程依次讲解接入、质量校验、状态维护和下游加工，
帮助你逐段核对数据是否按预期流转。

当前单元先完成这条链路的最小实例：使用已准备好的十笔订单，写入一张表，查询并核对每日金额。

### FE 与 BE

本课用一个 Docker 容器运行 FE 和 BE 两类服务，采用存算一体架构。
“一个容器”描述实验的部署方式，FE 和 BE 各自承担不同的数据库职责。

| 组件 | 本实验中的职责 | 如何观察 |
| --- | --- | --- |
| Notebook / SQL 客户端 | 提交 SQL，展示结果 | Lab 中的 SQL 单元 |
| Frontend（FE） | 接收 SQL、分析和规划查询，管理元数据并协调执行 | 连接 FE 查询端口；SHOW FRONTENDS |
| Backend（BE） | 执行查询计划，并保存内部表数据 | SHOW BACKENDS；查询订单表 |

这里的“元数据”是数据库用来描述和管理数据的信息，例如表名、字段类型和数据分布。
可以用一句话区分：`order_amount` 是金额列、类型是什么，属于表的定义；
订单 4 的金额为 445.20，则是表中的业务数据。

以“按日期汇总订单金额”为例，一次查询可以这样理解：

1. Notebook 将 SQL 发给 FE。
2. FE 解析 SQL，确认表和字段，生成执行计划，并协调计算任务。
3. BE 按计划读取订单数据，执行扫描、聚合等计算。
4. 查询结果返回客户端，由 Notebook 展示为表格。

多 BE 环境可以把计算任务分配给多个节点。本课先用一个 BE 观察完整流程，
单容器中的单副本表用于练习；生产部署还需要规划节点容量、副本与故障恢复。
Doris 的另一种部署方式是存算分离，业务数据保存在共享存储中，由计算节点访问。
两种模式的组件和存储位置见[系统架构](https://doris.apache.org/docs/4.x/features-architecture/system-architecture/)。

## 1.3 基础 SQL 与订单分析

### 认识本节的 WWI 历史订单

Microsoft Wide World Importers（WWI）是微软的模拟批发业务样例，包含订单、客户、商品、
发票和账款。本课从中选取十笔订单，整理为一张便于入门分析的订单表。
样本及来源说明随课程提供，详见[数据说明](../../datasets/README.md)。

先问一个建模时最重要的问题：**这张表的一行代表什么？**

本节答案是“一笔订单”。一笔订单可以包含多种商品，课程样本先把这些商品明细的税前金额相加，
得到订单金额，再把订单日期、客户号等字段放在同一行。这就是本表的“数据粒度”。

| 字段 | 含义 | 本节口径 |
| --- | --- | --- |
| order_id、customer_id | 原始订单、客户标识 | 订单号 1–5、80–84 |
| order_date | 原订单日期 | 2013-01-01 与 2013-01-02 |
| order_amount | 明细 Quantity × UnitPrice 合计 | 每笔订单的税前金额 |
| line_count | 对应商品明细的行数 | 一笔订单包含几条商品明细 |
| data_source | 数据来源 | WWI；后续新增模拟订单用 COURSE_SIMULATION |

例如，订单 4 的金额来自三条商品明细：

| 商品编号 | 数量 | 单价 | 税前金额 |
| --- | ---: | ---: | ---: |
| 206 | 96 | 2.70 | 259.20 |
| 130 | 5 | 32.00 | 160.00 |
| 50 | 2 | 13.00 | 26.00 |
| 合计 | | | 445.20 |

因此，`orders_sample` 中订单 4 占一行，`order_amount` 为 445.20，`line_count` 为 3。
统计本表行数得到订单数；把 `line_count` 相加则得到商品明细行数。
换成逐条商品明细的数据表后，一笔订单会占多行，订单计数就需要按订单标识设计。

金额也需要明确口径。本表的 `order_amount` 记录商品数量乘单价的税前合计。
收款金额需要支付或账款记录支持，含税发票金额需要发票数据支持。
本节先围绕“样本订单的税前金额”分析，D05 再导入十张完整历史业务表，扩展到多表分析。

### 读懂第一张表的定义

Lab 中会执行完整的 CREATE TABLE 和 INSERT。读建表语句时，可以按下面四个问题逐项理解。

第一，字段保存什么值？订单号和客户号使用 BIGINT；日期使用 DATE；
金额使用 `DECIMAL(18,2)`，共可表示 18 位十进制数字，其中两位为小数。
选定日期和金额类型后，就可以直接做日期分组和金额运算。
本课的字段均声明 NOT NULL，样本为每个字段提供完整值。
[Doris 数据类型](https://doris.apache.org/docs/4.x/table-design/data-type/)

第二，同一订单号再次写入时怎么办？本表采用 `DUPLICATE KEY(order_id)`。
这个模型保留写入的记录，键列参与排序；相同键值的记录可以同时存在。
它适合本节观察“写入了哪些行”，也让你能直接看到重复写入对统计的影响。
[Duplicate Key 明细模型](https://doris.apache.org/docs/4.x/table-design/data-model/duplicate/)

第三，数据如何分布？`DISTRIBUTED BY HASH(order_id) BUCKETS 1` 指定按订单号哈希分桶，
本实验使用一个桶。第四，保留几份副本？`"replication_num"="1"` 指定一份副本，
匹配本课的单 BE 教学环境。D03 会用对照实验进一步解释模型和分桶。

完成 Lab 建表后，可以查看实际定义：

```sql
SHOW CREATE TABLE orders_sample;
```

在输出中找到字段类型、`DUPLICATE KEY`、分桶和副本设置，将它们与 Lab 的建表代码对应起来。
这比只看到“创建成功”多了一步：确认数据库实际创建的是你想要的表。

### 从一笔订单开始读 SQL

以下查询均在完成 Lab 的建表和十行写入后执行，使用同一个实验库。
先查询刚才手工算过的订单 4：

```sql
SELECT order_id, customer_id, order_date, order_amount, line_count
FROM orders_sample
WHERE order_id = 4;
```

`FROM` 指定数据表，`WHERE` 选择订单 4，`SELECT` 指定展示字段。
在本课初始化数据下，预期结果是：

| order_id | customer_id | order_date | order_amount | line_count |
| --- | --- | --- | --- | --- |
| 4 | 57 | 2013-01-01 | 445.20 | 3 |

可以从中读出：客户 57 在 2013-01-01 下的这笔订单包含三条商品明细，税前金额为 445.20。
先把一行数据解释清楚，再扩展筛选条件和汇总范围。

### 筛选需要关注的订单

运营希望查看金额至少为 1000 的订单，可以写：

```sql
SELECT order_id, order_date, order_amount
FROM orders_sample
WHERE order_amount >= 1000.00
ORDER BY order_id;
```

`>=` 包含恰好等于 1000 的记录，`ORDER BY order_id` 按订单号稳定展示结果。
这个查询仍然保持一行一单，只缩小了返回的订单范围。

| order_id | order_date | order_amount |
| --- | --- | --- |
| 1 | 2013-01-01 | 2300.00 |
| 80 | 2013-01-02 | 1138.00 |
| 83 | 2013-01-02 | 6220.40 |

这三笔订单的税前金额合计为 9658.40。实验中的金额筛选练习会要求你自行完成这一查询并核对结果。

### 从订单明细变成每日汇总

现在回到运营的第一个问题：“每天有多少订单，金额是多少？”
需要把输出粒度从“一行一笔订单”改为“一行一个日期”：

```sql
SELECT order_date,
       COUNT(*) AS sample_orders,
       SUM(order_amount) AS order_amount
FROM orders_sample
GROUP BY order_date
ORDER BY order_date;
```

理解这段 SQL 时，先从数据如何形成结果入手：

1. 从 `orders_sample` 读取十行订单。
2. `GROUP BY order_date` 将相同日期的订单归到同一组。
3. `COUNT(*)` 计算每组的行数，`SUM(order_amount)` 计算每组金额合计。
4. `SELECT` 列出日期与指标，`AS` 为结果列起名。
5. `ORDER BY order_date` 按日期排列最终结果。

这是帮助理解结果的逻辑过程，数据库会自行选择实际执行计划。
其中 GROUP BY 决定汇总粒度，ORDER BY 决定展示顺序。
[SELECT 语句参考](https://doris.apache.org/docs/4.x/sql-manual/sql-statements/data-query/SELECT/)

以 2013-01-01 为例，这一组包含订单 1–5。订单数为 5，金额计算为
`2300.00 + 405.00 + 90.00 + 445.20 + 704.00 = 3944.20`。
两天的结果及人工核对合计如下：

| 日期 | 样本订单数 | 税前订单金额 |
| --- | ---: | ---: |
| 2013-01-01 | 5 | 3944.20 |
| 2013-01-02 | 5 | 8276.40 |
| 合计 | 10 | 12220.60 |

SQL 返回两行日期汇总；表中的“合计”行用于人工对账，12220.60 是这十笔样本的总金额。

这里有两个常见的 SQL 误区。只写 ORDER BY 会改变明细的顺序，仍然逐笔返回订单；
按 order_id 分组则是在订单粒度计算，无法得到每日一行的汇总。
每次写聚合查询前，先说出“结果的一行代表什么”，再选择 GROUP BY 列。

### 先筛选，再汇总，回答的是哪个问题？

把金额筛选与每日汇总放在一起：

```sql
SELECT order_date,
       COUNT(*) AS selected_orders,
       SUM(order_amount) AS selected_amount
FROM orders_sample
WHERE order_amount >= 1000.00
GROUP BY order_date
ORDER BY order_date;
```

这条查询回答“每天金额至少为 1000 的订单有几笔、合计多少”。
WHERE 先限定参与统计的订单，再按日期汇总，因此每天的金额只包含符合条件的订单。

| 日期 | 筛选后订单数 | 税前订单金额 |
| --- | ---: | ---: |
| 2013-01-01 | 1 | 2300.00 |
| 2013-01-02 | 2 | 7358.40 |

可以对照上一张每日汇总表，说明为什么订单数和金额发生了变化。
如果问题改为“找出每日总金额至少为 8000 的日期”，应先汇总全部订单，再用
`HAVING SUM(order_amount) >= 8000.00` 筛选分组。本样本中符合条件的日期为 2013-01-02。
WHERE 选择参与计算的明细，HAVING 选择计算后的分组，二者对应不同的业务问题。

### 如何判断结果可信？

一次分析至少要核对三件事：输入范围、统计口径和数据内容。
本节输入范围是指定的十笔样本，统计口径是税前订单金额，数据内容包括订单号、客户号、日期等字段。

先检查整体规模：

```sql
SELECT COUNT(*) AS order_count,
       SUM(order_amount) AS total_amount
FROM orders_sample;
```

初次完成 Lab 写入后，预期为十行、12220.60。接着回到明细，按订单号排序，
逐笔比较样本中的字段。两笔金额一增一减可能让总额保持相同，客户号或日期错误也可能不改变总额。
因此，Lab 同时提供总量检查和逐行检查，帮助你定位差异。

再想一个容易在 Notebook 中发生的情况：完整初始化后，又单独运行了一次十行 INSERT。
Duplicate Key 表会继续保留这十行，表中就有二十行，金额变为 24441.20。
这体现了表模型的追加语义。需要检查重复记录时，可以执行：

```sql
SELECT order_id, COUNT(*) AS copies
FROM orders_sample
GROUP BY order_id
HAVING COUNT(*) > 1
ORDER BY order_id;
```

本课正常初始化后，这条查询返回零行；重复写入整批后，十个订单号都会显示 `copies = 2`。
想重新开始实验时，先确认表中只有可重建的教学数据，再按 Lab 的“建表 → 写入 → 校验”步骤执行。
其中建表步骤会重置 `orders_sample`。生产数据的重试与去重则需要设计相应策略，D05 和 D07 会继续讲解。

最后，用完整的口径描述结果：“WWI 十笔样本在两天内的税前订单金额合计为 12220.60。”
收款、含税收入和全量经营日报分别需要对应的数据范围与业务事实支持。

## 单元总结

- 交易处理关注业务操作的正确完成；分析处理关注一批数据的统计与探索，访问范围和结果粒度需要分别理解。
- Doris 接收业务数据，组织明细与指标，并向分析用户提供 SQL 查询；持续接入需要配置对应任务。
- FE 接收 SQL、规划和协调查询；本节存算一体环境中的 BE 保存内部表数据并执行查询。
- 第一条分析路径是连接、建表、写入、查询和核对；WHERE 筛选明细，GROUP BY 决定汇总粒度，ORDER BY 决定展示顺序。
- 数据核对需要同时检查输入范围、金额口径和明细内容；本节十笔样本的税前订单金额为 12220.60。
