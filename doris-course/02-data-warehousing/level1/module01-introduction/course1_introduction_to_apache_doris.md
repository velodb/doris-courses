## D01-01：什么是 Apache Doris？

### 先区分交易与分析

客户点击“支付”时，业务系统需要判断订单是否存在、支付是否成功，以及是否允许
继续发货。这类围绕一次业务操作的处理通常称为联机事务处理（OLTP）。

运营查询“本周每天的订单金额”时，需要读取许多订单，按日期汇总。
这类工作通常称为联机分析处理（OLAP）。区别主要是工作方式，不是 SQL
最后返回了几行：一个金额总数也可能来自数百万行扫描。

| 业务问题 | 主要工作 | 本课程放在哪里 |
| --- | --- | --- |
| 用户能否成功下单、支付？ | 校验并提交业务操作 | 源交易系统 |
| 每天有多少订单？ | 扫描明细并分组计数 | Doris 分析层 |
| 退款后报表是否正确？ | 接收变更、维护状态、重新计算指标 | 后续订单数仓实验 |

Doris 是面向分析的数据库，提供 SQL 和 MySQL 兼容协议接口。已有 SQL 客户端
可以通过这一协议连接 Doris，但协议兼容不代表它就是 MySQL，也不代表所有
MySQL 功能和事务语义都相同。本课程不会把订单交易系统迁入 Doris。

### Doris 位于数据到业务结果的哪一段？

```text
订单、支付等业务系统
        ↓ 历史导入 / 持续变更
      Doris
        ↓ 清洗、组织数据、SQL 分析
    分析师 / 业务看板
```

数仓不是“把数据复制进来”就结束了。同一个订单被重复投递两次，如果直接相加，
报表可能翻倍；订单退款后，如果只保留最初记录，报表可能过时。
后续单元会逐步处理这些问题，当前先建立可以解释的正确基线。

### FE 与 BE

我们的实验环境使用存算一体架构：

| 组件 | 本实验中的职责 | 如何观察 |
| --- | --- | --- |
| Notebook / SQL 客户端 | 提交 SQL，展示结果 | Lab 中的 SQL 单元 |
| Frontend（FE） | 接收 SQL、分析和规划查询，管理元数据并协调执行 | 连接 FE 查询端口；SHOW FRONTENDS |
| Backend（BE） | 执行查询计划，并保存内部表数据 | SHOW BACKENDS；查询订单表 |

“容器已经启动”和“Doris 已能查询”不是同一件事。Lab 先检查连接和节点状态，
然后再建表、写入。SELECT VERSION() 可能显示协议兼容版本；
确认安装版本时，还要查看 FE/BE 返回的构建信息。

Doris 也支持存算分离架构，由计算节点访问远端存储。这是另一种部署选择，
不能用本节的单节点实验推断其扩缩容、隔离或故障恢复效果。D02 会进一步解释存储结构。

## D01-02：为什么用 Doris 构建订单数仓？

### 从数仓用户的工作出发

我们关心数据能否及时、准确地交给业务，而不是先记住执行引擎名称。
沿着一份订单数据的流转过程，可以提出下面的问题。

| 用户问题 | 本课程会学习的能力 | 学习位置 |
| --- | --- | --- |
| 历史文件和持续变化的数据怎么进来？ | 批量导入、Stream Load、持续接入路径 | D05；当前可执行实验先学习 Stream Load |
| 已有湖表一定要先搬进来吗？ | External Catalog 与外部数据查询 | D04，需讲师预置湖表 |
| 金额错误或订单重复怎么办？ | 导入校验、SQL 清洗、表模型与状态维护 | D03、D09-A、D06 |
| 新增维度一定要重建宽表吗？ | 多表 JOIN、聚合与灵活建模 | 后续 Level 2 |
| 如何把稳定的指标交给看板？ | 视图、物化视图和 BI 连接 | 后续 Level 2 |
| 补数和看板互相抢资源怎么办？ | Workload Group；存算分离下的计算资源管理 | 后续 Level 3 |

这些是课程的学习路线，不是本节已完成的功能清单。
选择哪种接入和建模方式，取决于数据来源、变化方式和业务要求。

### 认识本节的 WWI 历史订单

WWI 是微软的模拟批发业务样例，包含订单、客户、商品、发票和账款。
本课程围绕这些业务表，学习数据接入、关联分析与业务变更处理。
D01 从十笔订单的投影开始，D05 再导入 10 张完整历史表，共 701,846 行。

| 字段 | 含义 | 本节口径 |
| --- | --- | --- |
| order_id、customer_id | 原始订单、客户标识 | 订单号 1–5、80–84 |
| order_date | 原订单日期 | 2013-01-01 与 2013-01-02，不改成今天 |
| order_amount | 明细 Quantity × UnitPrice 合计 | 未含税，合计 12220.60，不是收款 |
| line_count | 对应商品明细的行数 | 明细数不是订单数 |
| data_source | 数据来源 | WWI；后续新增模拟订单用 COURSE_SIMULATION |

这里没有逐订单支付字段，不能推断订单未支付或全部支付。
WWI 客户账款中的收款不直接关联发票，不能强行分摊到订单。
后续模拟订单独立编号，引用同一批客户和商品，不改写原始历史。

### 第一张表为什么使用 Duplicate Key？

本节创建 d01_orders，显式写出字段类型、表模型、分桶和副本数。
`DUPLICATE KEY(order_id)` 的键用于排序，**不会约束订单号唯一**。
重复执行相同的 INSERT 会再追加一份记录。

因此，Lab 把“重建本节表”和“写入十笔数据”作为一次完整的初始化流程。
不能把反复追加理解成安全重试，也不能用这张表直接维护订单最新状态；
D03 和 D06 会分别解释模型选择与当前状态维护。
模型语义参考 [Duplicate Key 官方说明](https://doris.apache.org/docs/4.x/table-design/data-model/duplicate/)。

### 如何判断结果可信？

先核对所有字段，再按日期汇总。这只是十笔子集，不是两天的全部营业额。
完成 Lab 1 的初始化后，在同一实验库执行：

```sql
SELECT order_date,
       COUNT(*) AS sample_orders,
       SUM(order_amount) AS order_amount
FROM d01_orders
GROUP BY order_date
ORDER BY order_date;
```

这张表一行是一笔订单，因此 COUNT(*) 可以计数订单；若换成订单明细表，
一笔订单可能占多行，就不能直接沿用这个计数方法。
GROUP BY 将同一天的订单分为一组，SUM 计算组内金额，ORDER BY 让日期顺序稳定。
预期结果如下：

| 日期 | 样本订单数 | 税前订单金额 |
| --- | ---: | ---: |
| 2013-01-01 | 5 | 3944.20 |
| 2013-01-02 | 5 | 8276.40 |
| 合计 | 10 | 12220.60 |

两笔错误可能相互抵消，因此金额总数相同仍不足以证明明细正确。完整历史日报在 D05 执行。

## 单元总结

- 下单、支付提交是交易操作；按日期统计许多订单是分析操作，结果只有两行也可能需要扫描大量明细。
- Doris 在本课程中接收业务数据并提供分析，源系统继续负责交易；MySQL 协议兼容不代表所有 MySQL 行为相同。
- FE 接收 SQL、规划和协调查询；本节存算一体环境中的 BE 保存内部表数据并执行查询。
- 第一条分析路径是连接、建表、写入、查询和核对；GROUP BY 决定汇总粒度，ORDER BY 决定展示顺序。
- 十单样本税前金额为 12220.60，不代表完整两天的营业额，也不能推断收款；核对总量后还要核对明细。
